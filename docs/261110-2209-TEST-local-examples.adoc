The JEDEC evaluator is deliberately limited to these two example architectures. It reads
the assembled fuses rather than re-evaluating the source equations. For the registered
22V10 it accounts for inverted internal feedback, checks the two registered cell modes,
checks the combinational FLAG mode and verifies that EXT's output driver is disabled.
It evaluates next-state behavior for every current state; it does not simulate physical
clock edges, propagation delay, metastability or power-up. The Verilog simulation checks
clocked behavioral semantics separately. Neither is a hardware test.

The GAL16V8 test uses six relevant inputs; varying unused low address bits would add no
decoder coverage because the design does not consume them. The 22V10 test uses RESET,
LOAD, D0, D1, EXT and both current state bits. Its reset is synchronous, not the chip's
dedicated asynchronous reset. Both examples use continuously driven outputs.

== Reproduce

From the workspace root:

[source,shell]
----
python3 tools/check_gal.py
bash tools/check_verilog.sh
----

The first command builds the local GALasm checkout with GCC, copies our `.pld` files
into `output/gal/`, assembles them and verifies the results. Files `.jed`, `.pin`, `.chp`
and `.fus` are retained there. The second prefers system Icarus tools when available;
otherwise it uses the extracted project-local package with an explicit backend path.
The design is ordinary Verilog; `-g2012` is used for the testbench's failure handling.
`reports/validation.json` and the adjacent logs record the final execution and hashes.

== Archived primary documents checked

The Quartus archive directory is documented in the main report. Its Linux TAR member
list was read and confirms the base installer and MAX device package; the archive was
not fully extracted or installed. The local handbook was text-extracted and its relevant
page was rendered and inspected:

----
/home/falken/_/wrk/prj/260707 vmexcalc ali - AL-2301 DJ-2301/!! -- ALTERA Quartus 130sp1webfree/quartusii_handbook_archive_130.pdf

At physical PDF page 796, printed Volume 1 page 18-2, its Synplify flow note states that
Quartus versions 10.1 and later require TimeQuest; Classic timing examples refer to
10.0 and earlier. This corrects an easy mistake when adapting very old MAX examples to
the 13.0 SP1 toolchain. There is no claim here that the bundled, unconstrained project
has met any timing requirement.

Also checked the archived vendor MAX 3000A datasheet, June 2006 version 3.5:

----

Its Table 1 gives the 64/128 macrocell capacities; the architecture section describes
one configurable register per macrocell. Its I/O discussion distinguishes 5 V tolerant
inputs from 2.5/3.3 V output supplies. The first page was rendered and visually checked
against text extraction. Local inventory labels establish which package markings were
recorded, not that any particular physical chip has been identified or tested today.

== Remaining for a board-ready Altera design

Install/select the appropriate Quartus version and device package; finalize a real
controller specification; supply package pin, I/O voltage and clock/interface timing
constraints; run synthesis, fitting and timing review; then program and test the actual
board. Until then the prepared Tcl project is a study template, and the generated GAL
JEDEC files have illustrative pin assignments. The 7xsys MMU has not been implemented
or fitted by this task.
